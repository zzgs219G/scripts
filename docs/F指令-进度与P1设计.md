## 0. 背景与硬约束（不可丢）

- **角色**：用户是产品经理，**不写代码**，只有一点逆向经验，能看懂逻辑，无法自己改代码。
- **`f` 是什么**：用户在手机 Termux 里跑的自研脚本（`fz-tools/modules/burn.sh`，别名 `f`）。
  它把一个项目的源码按规则过滤后**拼成一个大 txt**，喂给对话框 AI 做全项目分析、产出计划书。
- **硬约束（改动时不得违反）**：
  1. **一次 `f` = 一次打包 = 一次分析**，绝不允许"来回多轮要文件"（用户明确否决过）。
  2. 输出必须**自解释**——用户看不懂代码细节，但产物结构要让他和 AI 都能一眼抓骨架。
  3. 不新增外部依赖（只用 git / awk / sed / find / grep），保持跨平台（Termux/PC）。
- **痛点**：项目变大后（1MB→2MB→3MB），全量 txt 质量下降，AI 分析不准。
- **根因（已实测定位）**：`f` 的目录树 `find -maxdepth 3` 从**仓库根**算深度，
  而 Android 源码在第 **7** 层（`app/src/main/java/com/xixin/box/…`）→
  **目录树一个业务包都没命中**，AI 打开 txt 看不到骨架。

### 1.4 P1-1b 实测中发现并修复的 2 个真实缺陷

符号索引端到端跑通后，输出里出现一行 `//  FUN   Application.` ——由此挖出两个**先前的正则缺陷**：

| 缺陷 | 现象 | 根因 | 修复 |
|---|---|---|---|
| **B4 中文标识符被截断** | `fun Application.初始化版本()` → 索引里只剩 `Application.` | 正则用 `[A-Za-z0-9_.]` 匹配标识符，**不匹配中文**。而本项目确实用了中文类名/函数名（`object 云服务配置`、`fun Application.初始化版本`） | 改用 `[^[:space:]({<:]+` / `[^[:space:](]+`（**排除法**而非白名单枚举），对 Unicode 通用 |
| **B5 非 Kotlin 文件被误扫** | 索引/入口表里出现 `docx/APP架构与流程文档.md` 的条目（把 markdown 当 Kotlin 解析） | 入口表与符号索引未按扩展名过滤，直接吃 `_f_burn_scan` 的全量输出 | 两处 awk 前加 `grep -E '\.(kt|kts)$'` |

修复后实测：符号索引 **623 行 / 54KB**（占成品 4.8%），中文符号 2 条**完整保留**，`.md` 垃圾条目 **0 条**。

→ 教训：`f` 的产物本身是**最好的回归测试**。任何新段落都要肉眼扫一遍尾部/边界 —— 上面这个 B4 就是靠 `tail -3` 抓出来的，跑通 ≠ 正确。

## 2. P1 设计（未完成 —— 下一步要做的）

### 2.1 目标

把 `f` 从「**全量原文拼接**」升级为「**三层结构化打包**」：
体积↓、AI 可读性↑、**体积增长曲线从线性改为次线性**（这样才能扛到 3MB/5MB）。

### 2.2 三层结构（一次 `f` 打出，仍是单文件）

```
L1 骨架层（头部，~120KB，近对数增长）
   1.1 仓库概览（现有）
   1.2 源码结构树（P0 已做 ✅）
   1.3 符号索引：全量 class/object/interface 的 FQN → 文件（一行一条，可 grep）
   1.4 入口表：Application / Activity / NavHost / @Serializable 路由 / 全局单例
   1.5 依赖有向图：文件→项目内依赖；反向：被引用 TopN

L2 核心层（枢纽类【完整源码，含 KDoc】，~250KB，规模由 Top-N 封顶、与项目总量解耦）

L3 IR 层（其余文件：文件头 + 声明行【带行号锚点】，无函数体，~200KB）
```

### 2.3 关键设计决策

- **核心层判定规则（并集，可解释、可调参、可复算）**：
  被引用次数 ≥ 阈值 ∨ 入口类 ∨ 全局单例 ∨ `*ViewModel`/`*Repository`。
- **L3 的 IR 提取不做"剥离函数体"**（bash 里括号匹配太脆、风险高），
  改为**只输出"声明行"**：`class/interface/object/enum/fun/val` 等以正则识别的顶层与成员声明行，
  **保留行号锚点**。鲁棒、简单、够用。
- **渐进披露闭环**：L3 的行号锚点 + 现有已支持的 `f <关键词>`（定向打包）
  → AI 说"把 `X.kt` 的 120–200 行发我"，用户直接跑 `f X`。**无需新命令、无需多轮**。
- **回滚**：新增 `f --legacy`（或环境变量）保留旧全量行为，便于对比与回滚。
- **红线**：主文件头部必须**显式声明**「哪些文件进了 L2 全文、哪些只给了 L3 签名、排除了什么、是否截断」。
  任何静默裁剪都是危险的——AI 会基于不完整信息自信地犯错。

### 2.4 体积预算（jian_box 预估）

| 层 | 预估 | 增长性质 |
|---|---|---|
| L1 骨架 | ~120 KB | 近似 O(符号数)，近对数 |
| L2 核心层全文 | ~250 KB | Top-N 封顶，不随项目线性涨 |
| L3 其余文件 IR | ~200 KB | O(接口数)，约全文的 25% |
| **合计** | **~570 KB** | 比现状 **−43%**；项目翻倍时约 ×1.3~1.5（现状 ×2） |
