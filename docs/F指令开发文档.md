一、问题重新定义

所以要加的不是"砍代码"，是在代码前面塞一份"结构雷达"。

二、我建议的改造：保持全量，加三层"结构信号"

信号 1：顶部加「热点类排行榜」（脚本自动算）

扫描所有 .kt 的 import com.xixin.box.* 行，统计每个项目内 FQN 被引用的次数，输出 Top 30。

```kotlin
/* ── 项目内热点类（被 import 次数 Top 30）── */
//   1. AppJsonConfig          被 78 个文件引用
//   2. AppLogger              被 64 个文件引用
//   3. GlobalDownloader       被 41 个文件引用
//   4. ...
```

为什么这个最重要：我一看这个排行榜就知道哪几个类是"总线"，你项目改任何一个功能，都要先想清楚对这几个类的冲击面。没有这个排行榜，我得翻遍全文才能拼出这张图。

信号 2：每个文件头部加「项目内依赖摘要」

现在文件头只有：

```
// 📄 [wrapper/engine/download/GlobalDownloader.kt]
```

改成：

```
// 📄 [wrapper/engine/download/GlobalDownloader.kt]
// ├─ 项目内依赖: AppConstants, AppLogger, NetworkClient, AcwShield, AcwWebViewBypass, LanzouRedirectPage, FileProvider...
// └─ 被引用: TaskViewModel, ApkProtectViewModel, MediaDownloadHelper, LzyFileDetail, BoxVideoPlayer...
```

为什么这个有用：我看一个文件时，一眼知道它的上下游。以前我得靠猜"这玩意谁在用"。

「被引用」这一栏怎么算：脚本先扫一遍全文建立"符号→文件"的 map，再扫一遍每个文件的内容里出现哪些符号。对你项目体量（500 文件）来说秒级完成。

信号 3：目录树升级为「目录仪表盘」

现在：

```
wrapper/
  engine/
    download/
    network/
  ui/
    m3e/
    components/
```

改成：

```
wrapper/                          ← 共 87 文件 · 12400 行 · 主要导出: NetworkClient, GlobalDownloader, BoxVideoPlayer, AppLogger, AntiCapture
  engine/                         ← 31 文件 · 主要导出: R2Uploader, GitHubDispatcher, WebVideoSniffer
    download/                     ← 8 文件 · 主要导出: GlobalDownloader, AcwShield, MediaDownloadHelper
    network/                      ← 5 文件 · 主要导出: NetworkClient, R2Uploader, GitHubDispatcher
  ui/                             ← 42 文件 · 主要导出: ToolPrimaryButton, CommonListPage, AppLoadingIndicator
    m3e/                          ← 12 文件
    components/                   ← 4 文件
```

为什么有用：以前我看目录树只知道"有这个目录"，不知道"这个目录负责啥、重量多大"。加了「主要导出」，目录树瞬间变成架构地图。

---

三、具体做法（一句话概括）

保持全量打包不变，只是在 txt 的头部和文件头部，把脚本本来就能算出来的结构信息显式写出来。

在 burn.sh 里加三件事：

1. 打包第一遍（新增）：扫描全部待打包文件，建两个表——「符号 → 文件」「文件 → 项目内依赖」，顺便统计热点排行榜
2. 写头部（改现有）：在目录树之后、正文之前，插入热点排行榜
3. 写文件头（改现有）：// 📄 [路径] 下面加两行依赖/被引用摘要

文件正文一个字都不删，只是在它前面塞了 3 层标签。

---

四、这样能解决什么

你说的痛点 加了结构信号后
"5 万行我挑不过来" 打开先看热点排行榜——知道哪 30 个类是核心
"分析越来越不准" 每个文件自带上下游，我不用从调用点反推
"不知道一个功能改了会波及谁" 目录仪表盘 + 热点榜，一眼看清冲击面
"不想来回让你点名要文件" 不需要——全量还在，只是前面多了雷达图

代价：txt 会增加大概 5%~10% 体积（热点榜几百行 + 每文件两行摘要）。但换来的，是我第一眼就抓住骨架的能力。

不做的事：

· 不砍正文（会丢信息）
· 不做 Compose Modifier 链压缩（有损，风险高）
· 不拆多模块（上一轮已论证，不是当下的堵点）
